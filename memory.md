# Project Memory — MMR Passport Renewal Monitoring System

This file is a standing record of the project's purpose, architecture, decisions,
and history, so anyone (including a future AI session) can pick the project back
up without re-deriving context from scratch. It is not user-facing — see
`userGuide.md` for that.

## What this is

A free, volunteer-run tool that watches two things the Myanmar Embassy in
Singapore publishes and sends a Telegram alert the moment a watched person's
name/passport appears, so people don't have to manually check every week:

1. **The embassy website's Lost & Seaman/Offshore approved-list PDF.**
2. **The `@mesg15` Telegram channel's PV/PJ renewal appointment posts** — the
   actual standard passport-renewal list most people need; confirmed by direct
   inspection that the embassy website itself does not publish this one.

Originally scoped as a personal tool (the developer's own name on a watchlist),
it evolved during the build into a public community service anyone can sign up
for.

## Architecture

Three independently deployed pieces, one repo:

```
checker/    Python pipeline (fetch -> OCR/extract -> parse -> match -> notify)
            runs on GitHub Actions (cron, every 3h) because OCR needs the
            tesseract + poppler system binaries, which Render's free runtime
            can't install without Docker, and Actions never idles-out the
            way Render's free tier does.
backend/    FastAPI REST API over Neon Postgres, deployed to Render.
frontend/   React + Vite + TS + Tailwind, deployed to Vercel.
```

Data flow:

```
GitHub Actions (every 3h)
  -> conditional GET embassy PDF (ETag/Last-Modified) + Telethon fetch of
     new @mesg15 posts
  -> OCR/parse both sources
  -> match against watchlist (passport-number authoritative)
  -> write to Neon Postgres
  -> Telegram alert to matched users + the operator

Vercel frontend <--Bearer token (admin only)--> Render FastAPI <--> Neon Postgres
```

## Key decisions and why

- **Matching is passport-number-only for the embassy PDF (`match_row`)**,
  not "name AND passport." Originally required both, but OCR mangles names
  often enough (especially long Burmese names) that requiring a name match
  too was silently dropping real matches. A passport hit alone is now
  sufficient and reported; the name is still shown/compared for display and
  flagged as `name+passport` vs `passport` confidence, but is no longer a
  gate.
- **The `@mesg15` renewal list (`match_renewal_row`) is the deliberate
  exception: it requires BOTH the masked passport's visible digits AND a
  plausible name match.** The embassy redacts the middle 2 of 6 digits
  before posting, so two different real passport holders could
  coincidentally share the same visible letters + first 2 + last 2 digits
  -- unlike the full-passport PDF case, that ambiguity can never be told
  apart from the masked post alone, and the name is the only disambiguator
  available. User-requested tradeoff, made with the explicit downside
  understood: a genuine match with a badly OCR'd name on this specific list
  will now go unreported (the opposite tradeoff from `match_row` above).
- **Fuzzy name matching uses `rapidfuzz.fuzz.token_sort_ratio`, not
  `token_set_ratio`.** `token_set_ratio` produced false positives on Myanmar
  names that share a short base word (e.g. "KAUNG HTET" scored as a strong
  match against "KAUNG HTET KYAW," a different person, because
  token_set_ratio effectively ignores extra tokens). `token_sort_ratio`
  verified: genuine OCR typos still score >=90; different-person cases with
  an extra/missing name token score <=87.
- **Telethon (MTProto client API), not the Bot API, reads `@mesg15`.** The
  public no-login preview (`t.me/s/<channel>`) serves downscaled, recompressed
  photos with visibly worse OCR accuracy. Telethon, logged in as the
  developer's own account (read-only, same access as viewing the channel in
  the app), gets full-resolution originals. This requires a one-time
  interactive login (`checker/generate_session.py`) done locally, never in
  chat, producing a session string stored only as a GitHub Actions secret.
- **Admin auth is WebAuthn/Passkey, not a password.** No username/password
  exists; a device's Face ID/Touch ID-backed key pair is the credential. A
  one-time bootstrap secret (entered by hand, once) registers the very first
  device only, then becomes permanently useless. Additional devices are
  added via a 10-minute one-time enrollment code generated by an
  already-logged-in session — never by reusing that bootstrap secret.
- **Admin sessions use a Bearer token in `localStorage`, not a cookie.**
  Originally cookie-based; Safari's Intelligent Tracking Prevention silently
  drops cookies between the Vercel frontend and Render backend because they
  are different registrable domains. Symptom was "`TypeError: Load failed`"
  and the dashboard appearing logged in, then 401ing on every subsequent
  request — Chrome worked the whole time, masking the bug until the user
  specifically tested Safari. Switching to an `Authorization: Bearer <token>`
  header sent explicitly on every request fixed it outright, and is simpler
  (no `credentials: 'include'`, no cross-site cookie config needed).
- **Public signup requires no login at all** — this was an explicit, firm
  correction mid-build ("we are not asking users to login!"). Only `/admin`
  is gated. A person's own `lookup_token` (a random URL segment, emailed to
  no one, shown once at signup) is the only credential needed to check their
  own status later.
- **Re-submitting the same details does not create a duplicate.** `POST
  /api/watchlist` looks for an existing row matching on `telegram_chat_id` OR
  `passport_no` first; if found, it backfills any fields the existing row was
  missing (e.g. an admin-created entry that predates the Telegram field)
  rather than silently ignoring newly supplied details, and returns the
  existing record's `lookup_token` instead of minting a new person.
- **PII is masked server-side, not just in the UI.** `backend/schemas.py` has
  `mask_passport`, `mask_telegram_id`, `mask_name` — applied before the
  response ever leaves the API. This matters because the frontend's API base
  URL/key material is public (anyone can call the API directly), so a
  UI-only mask would be purely cosmetic.
- **Telegram connection + Terms acceptance are both required server-side**,
  not just UI gates, for the same reason as PII masking — a direct API call
  could otherwise bypass a client-side-only check. `terms_accepted_at` is a
  durable timestamp column, not a transient checkbox.
- **Signup dedup (`POST /api/watchlist`) requires the submitted name to
  plausibly match the existing record's name**, not just a `telegram_chat_id`
  or `passport_no` hit. Originally matched on either field alone — but
  neither is secret (a chat ID is shown by the bot to anyone who starts a
  chat with it; a passport number can be known without being controlled),
  so anyone submitting a known/guessed field got back that person's real,
  unmasked `full_name`, and could even backfill their own `telegram_chat_id`
  onto someone else's passport-only record, redirecting that person's future
  alerts to themselves. Fixed by requiring `names_plausibly_match()`
  (`checker/match.py`, the same `token_sort_ratio` logic used for
  embassy-list matching) between the submitted and stored name before
  treating a field hit as "this is the same person re-submitting."
- **The Telegram webhook secret (`TELEGRAM_WEBHOOK_SECRET`) is separate from
  `API_SECRET`**, not the same value reused. They were originally the same
  on the theory that `API_SECRET` becomes "permanently useless" once the
  first admin device is registered — true for the *bootstrap* use, but the
  webhook check (`backend/telegram_webhook.py`) used the same value forever,
  so a leaked `API_SECRET` would stay a live way to forge webhook calls
  indefinitely, not a one-time risk. `backend/auth.py::webhook_secret()`
  falls back to `API_SECRET` when the new var is unset, so existing
  deployments keep working until it's added on Render (see README).
- **Rate limiting (`backend/ratelimit.py`) is a plain in-process dict, not
  Redis-backed.** Matches how this is actually deployed: a single Render
  web-service instance, no `--workers`, so one process sees every request
  and nothing goes stale across instances. Applied to `POST /api/watchlist`
  (public signup) and the WebAuthn register/login endpoints -- the
  unauthenticated or security-sensitive ones worth slowing down for a
  script without inconveniencing a human. Keys on `X-Forwarded-For`, not
  `request.client.host`, since Render's edge proxy means the latter is the
  proxy's own address for every request, not the real caller's.
- **`POST /api/auth/logout-all` exists because revoking a Passkey device
  does not retroactively invalidate sessions already issued from it** --
  `AdminSession` isn't tied to a `credential_id`, so a leaked bearer token
  would otherwise stay valid for its full 30-day TTL even after the device
  that created it is revoked. This endpoint deletes every session row, the
  only way to kill a suspected-leaked token immediately.
- **Full names are stored and shown in ALL CAPS**, matching how names appear
  on Myanmar passports and on the embassy's own lists (avoids a mismatch
  between "as entered" casing and "as displayed on official documents").
- **One-tap "Connect Telegram" button, not a phone-number-based auto-reply.**
  Telegram's Bot API fundamentally cannot message a user who hasn't first
  started a conversation with the bot — there is no way to target someone by
  phone number or Telegram ID alone. The backend self-registers a webhook
  (`backend/telegram_webhook.py`) on every boot, pointed at its own Render
  URL, secured with a verification secret checked on an incoming-request header. Tapping "Connect Telegram" opens a chat with the bot;
  tapping Start triggers the webhook, which replies instantly with the
  user's chat ID (new user) or a welcome-back + status-link message
  (existing user, looked up by `telegram_chat_id`). This was chosen over a
  larger conversational-bot build as the best achievable UX given the
  platform constraint.

## Known data-format quirks (why the parsers look the way they do)

### Embassy website PDF (`checker/parse.py`)
- Alternates between a text-layer PDF (Excel export) and a scanned image
  needing OCR; `checker/extract.py` auto-detects which.
- "Passport No. / Other" column sometimes holds a seaman-book number
  (`SIRB-10245/24-12-2014`) or CDC number (`CDC3363`) instead of a standard
  passport number — a fallback identifier pattern catches these.
- Long/Burmese-script names sometimes wrap onto their own line above the
  index/ID line; the parser pulls the name from the previous line in that
  case.
- OCR occasionally misreads capital `I` as `!` — folded before matching.
- `tesseract --psm 4` reads these tables correctly; the default `--psm 6`
  returns garbage. This was the difference between unusable and reliable.
- Dates/indexes can appear in Burmese numerals (`၀၇-၀၉-၂၀၂၃`) or Latin
  (`28/9/2026`); Burmese digits are normalized to `0-9` before parsing, and
  the index column is never used as a parsing anchor (unreliable across
  formats) — passport-number regex is the anchor instead.

### Telegram renewal posts (`checker/parse_renewal.py`)
- Passport numbers are partially masked by the embassy for privacy
  (`MF 40**22` — middle 2 of 6 digits redacted). Matching checks the letters
  plus visible first/last 2 digits; a coincidental collision on the visible
  digits (different person) is theoretically possible but requires the name
  to also match, which is effectively never true for a genuinely different
  person.
- One appointment date per image, applied to every row on that image.

### Both sources
- A per-page/per-image integrity check compares the count of index markers
  against the count of successfully parsed rows. Any shortfall triggers a
  re-OCR at a different setting; if still short, the gap is recorded
  (`extraction_issues` table) and surfaced as a warning rather than silently
  treated as "no match." The explicit design rule: **never report "you are
  not on the list" when extraction was incomplete.**

## Debugging history worth remembering

- **Render build failures on pydantic-core** were a Rust-compile issue tied
  to the Python version Render picked; fixed by pinning `PYTHON_VERSION:
  3.12.7` in both `render.yaml` and a `.python-version` file. If a similar
  build failure recurs, check the Python version first before anything else.
- **"Telegram never sends a message" was debugged in layers, not one fix**:
  (1) the bot's credential was configured as a GitHub Actions secret but
  never as a Render environment variable — the live backend and the
  GitHub Actions checker are separate runtimes with separate secrets; (2) the dedup-on-resignup path
  found an existing entry but never backfilled the newly-submitted
  `telegram_chat_id` onto it, so no message was ever attempted; (3) Telegram
  API errors were caught by a bare `except Exception: log.exception(...)`
  and never surfaced anywhere the user could see them. All three had to be
  fixed before the symptom actually went away — if a similar complaint
  recurs, check env vars first, then the dedup path, then whether errors are
  actually being surfaced to the signup response (`telegram_sent` /
  `telegram_error` fields).
- **Vercel/CDN cache staleness was mistaken for a real bug** more than once
  during deploy verification via `curl` cache-busting. Asking the user to
  check the Vercel dashboard directly resolved it faster than continued
  polling.

## Current live configuration (as of this writing)

- Bot: `@MMR_PassportRenewalMonitoringBot`.
- Matching policy: passport-number alone is sufficient; name is informational.
- Public routes: `/` (signup + Lists/Alerts/Status tabs), `/status/<token>`.
  Admin-only: `/admin` (Passkey-gated).
- Signup now requires, server-side-enforced: non-empty `telegram_chat_id` and
  `terms_accepted: true` (see `backend/main.py::create_watchlist`).
